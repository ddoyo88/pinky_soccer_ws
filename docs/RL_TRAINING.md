# 강화학습 공격수: 설계와 학습 기록

규칙으로 짠 공격수(`striker.py`)는 동작이 딱딱 끊겨서 축구다운 느낌이 약했습니다. 그래서 **공격수의 판단 부분만** 강화학습 정책으로 바꿔 더 자연스러운 플레이를 만드는 것이 목표입니다. 이 문서에는 설계, 학습 순서, 시행착오, 단계별 결과를 시간 순서대로 남깁니다.

## 1. 전체 구조: 무엇을 바꾸고 무엇을 유지하나

```
카메라 → ball_detector ─┐
라이다 → AMCL ──────────┼─►  [ RL 정책: 작은 신경망 ]  ─► 속도 명령 (/cmd_vel)
바퀴·IMU → odom ────────┘        ↑ 기존 striker.py의 판단 자리
```

- **유지:** 공 인식, 위치 추정, 심판, 안전장치(흰 라인 가드, 벽 보호, watchdog), 경기 진행(준비, 세레모니, 재시작)
- **교체:** 공 뒤로 돌아가기 → 몰기 → 슛으로 이어지는 플레이 판단
- **카메라 영상을 직접 넣지 않는 이유:** 시뮬레이션 영상과 실물 영상은 많이 다릅니다. 영상을 그대로 입력하면 시뮬에서만 잘하는 정책이 되기 쉽습니다. 대신 "공이 로봇 기준 어디 있다" 같은 숫자를 입력합니다. 이 숫자는 시뮬과 실물에서 같은 형태라 옮기기 쉽습니다.

## 2. 학습 환경 (`src/pinky_soccer_rl/pinky_soccer_rl/env.py`)

- 경기 시뮬레이터(MuJoCo)와 **같은 로봇 모델·물리**를 씁니다: 공식 Pinky 모델, 범퍼, 바퀴 가속 한계, 구르는 골프공, 훈련용 경기장.
- ROS와 카메라 렌더링은 뺐습니다. 그래서 실시간보다 훨씬 빠르게 돌고, 8개 경기장을 동시에 돌립니다.
- 노랑이 +X 골대를 공격합니다. 한 시도는 30초입니다.

### 입력 (관측 17개 숫자): 실물 로봇이 가진 정보만
| 항목 | 내용 |
|---|---|
| 공 위치 (로봇 기준) | 카메라 시야(정면 ±29.5°, 0.10~1.6 m) 안일 때만 보임. 측정 잡음 포함. 안 보이면 마지막으로 본 위치를 기억 |
| 공이 보이는지, 마지막으로 본 뒤 지난 시간 | 공을 놓쳤을 때 찾는 행동을 배우게 함 |
| 내 위치·방향 | 위치 추정(AMCL)처럼 약 2 cm, 0.03 rad 잡음 포함 |
| 공격할 골대 방향·거리 (로봇 기준) | |
| 내 속도, 직전 행동 | 부드러운 운전 |
| 상대 로봇 위치 (로봇 기준) | 2단계부터. 라이다로 얻는 정보 |
| 공 속도 (로봇 기준, m/s) | **3단계부터** (입력 19개). 연속으로 본 카메라 공 위치의 차이로 계산(지수 평활). 안 보이면 서서히 0 |

### 출력 (행동 2개)
0.1초마다 **직진 속도**(최대 0.30 m/s)와 **회전 속도**(최대 4 rad/s)를 냅니다. 기존 공격수와 같은 10 Hz입니다.

### 보상과 감점
| 항목 | 값 | 의도 |
|---|---|---|
| 골 | **+10** (종료) | 최종 목표 |
| 자책골 | **−10** (종료) | |
| 공이 상대 골대에 가까워짐 | +5 × 줄어든 거리(m) (v1: 3) | 공을 골대로 운반 |
| **공 뒤 지점에 가까워짐** (v2) | +1 × 줄어든 거리(m). 공→골대 선 위, 공 뒤 12 cm 지점 | 공 뒤로 돌아가 정렬하기 |
| **수비 지점에 가까워짐** (3단계) | 공이 우리 진영에 있고 상대가 공에 더 가까우면, 목표를 "공에서 우리 골대 쪽 15 cm" 지점으로 바꿈 (+1/m) | 공과 우리 골대 사이 막기 |
| 로봇이 공에 가까워짐 | +0.5 × 줄어든 거리(m) | 초반 탐색 유도 |
| 공 터치 | 새로 닿을 때 +0.1 (1초에 한 번까지) | 공 다루기 |
| 시간 | 매 스텝 −0.005 | 빨리 넣기 |
| 행동 급변 | −0.02 × 변화량² | 부드러운 움직임 |
| 흰 라인 넘음 | 매 스텝 −0.1 | 경기장 밖으로 나가지 않기 |
| 막혀서 못 움직임 | 매 스텝 −0.03 | 벽·골대에 박치기하지 않기 |
| **충돌 순간** (3단계 v3) | 새로 닿을 때마다 **−5** | 상대 로봇을 장애물로 보고 피하기 |
| 상대 로봇과 접촉 중 (3단계 v2부터) | 닿아 있는 매 스텝 −0.2 (v1: 미는 경우만 −0.05) | 충돌 금지 (로봇 파손 방지) |
| 너무 가까움 (3단계 v3) | 중심 거리 25 cm부터 줄어들어 20 cm 이하에서 매 스텝 −0.05 | 미리 비켜 가기 |
| 로봇 가드에 막힘 (3단계 v3) | 매 스텝 −0.05 | 가드에 기대지 말고 스스로 피하기 |
| **로봇 넘어짐** (3단계 v2부터) | 30° 넘게 기울면 **−10, 종료** | 절대 뒤집히지 않기 |
| 공을 라인 밖으로 보냄 | −2, 공을 센터로 옮기고 계속 (v1: −1로 종료) | 실제 심판 규칙과 같게 |
| 시간 초과 (30초) | −1 | |

### 실물 차이를 견디게 하는 장치 (도메인 랜덤화)
매 시도마다 다음을 조금씩 다르게 합니다.
- 공 구름 저항: 0.0002~0.0005
- 바퀴 반지름 오차: ±3% (보정 전 실물처럼)
- 카메라 측정 잡음: 0.5~2 cm × (1 + 거리)
- 명령 지연: 0~0.1 s

### 시작 상황
- 25%는 실제 경기처럼 시작 위치에서 센터 공을 노립니다.
- 75%는 공과 로봇이 경기장 안 무작위 위치에서 시작하고, 로봇 방향도 무작위입니다.

## 3. 학습 방법: PPO (stable-baselines3)

1. 8개 경기장에서 30초짜리 시도를 동시에 계속 돌립니다.
2. 512스텝 × 8개 경기장 = 4,096스텝마다 신경망을 고칩니다. 신경망은 은닉층 256-256이고, 정책과 가치 함수가 각각 따로 있습니다.
3. 결과가 예상보다 좋았던 행동은 확률을 올리고, 나빴던 행동은 내립니다. PPO는 한 번에 너무 많이 바뀌지 않게 제한합니다(clip 0.2).
4. 10만 스텝마다 무작위성을 끄고 같은 20개 상황으로 시험합니다. 골 비율, 자책골, 라인 넘음 비율, 골까지 걸린 시간을 기록합니다.
5. 입력과 보상은 정규화(VecNormalize)하고, 그 통계도 정책과 같이 저장합니다. 실물에 올릴 때 같은 통계를 써야 하기 때문입니다.

## 4. 학습 순서 (커리큘럼)

| 단계 | 상대 | 목표 | 상태 |
|---|---|---|---|
| 1 | 없음 | 공을 찾아가 골대에 넣기, 라인 지키기 | **완료**: 골 85% (규칙 컨트롤러 55%) |
| 2 | 규칙 상대: 공 뒤로 가서 우리 골대 쪽으로 밂 (0.12 → 0.18 m/s 커리큘럼). 시도의 60%에서 등장 | 상대를 피해 공 뺏기·넣기, 라인 가드에 적응 | **부분 완료**: 혼자 95%, 상대 있을 때 수비 약함 |
| 3 | 기존 규칙 기반 striker | 실제 경기 시뮬(sim_duel)에서 비교 | **완료: 5 : 0 승** |
| 3' | **수비 + 셀프 플레이**: 규칙 상대(0.18 m/s) 또는 고정된 과거 정책. 시도의 75%에서 상대 등장 | 공 속도 보기, 수비 위치 잡기, 서로 다투는 1:1 | 진행 중 |

마지막으로 학습한 정책을 `rl_striker` ROS 노드로 만들어 기존 `striker`와 바꿔 끼웁니다. 순서는 시뮬 경기 → 실물 1대 → 실물 2대 경기입니다.

### 비교 기준 (같은 20개 시험 상황)
| 컨트롤러 | 골 | 자책골 | 라인 아웃 | 시간 초과 | 라인 넘은 스텝 |
|---|---|---|---|---|---|
| 손으로 짠 단순 컨트롤러 (정답 위치 사용), 1단계 | 11/20 | 0 | 2 | 7 | 17.8% |
| 같은 컨트롤러, 2단계 상대 있음 | 0/20 | 3 | 3 | 14 | 2.2% |

## 5. 시행착오 기록

### 학습 속도가 코어 수만큼 늘지 않음 (2026-11-24)
- **증상:** 경기장 8개를 동시에 돌려도 초당 스텝 수가 1개일 때와 같았습니다(약 140 스텝/s).
- **확인한 것:**
  - CPU 제한(cgroup)은 없었습니다.
  - 순수 파이썬 계산은 코어 수만큼 잘 늘었습니다.
  - 공식 로봇 1대 모델도 잘 늘었습니다.
  - 그런데 우리 경기장 모델은 접촉 계산을 모두 꺼도 늘지 않았습니다.
- **원인:** 화면용 3D 메시(정점 74만 개, 면 89만 개, 모델 173 MB)가 물리 계산 메모리에 같이 실려 있었습니다. 여러 프로세스가 CPU 캐시와 메모리 대역폭을 두고 다툰 것으로 추정합니다.
- **해결:** 학습용 모델에서 화면 전용 요소를 모두 뺐습니다(경기장 그림 라인, 시각 메시, LCD 화면). 충돌 모양은 그대로 둬서 물리는 같습니다(173 MB → 24 MB).
- **결과:**
  - 1개 프로세스 기준 2배 빨라졌고, 4개 프로세스 합계는 약 1만 → 5.6만 물리 스텝/s가 됐습니다.
  - 학습 환경은 8개 병렬로 573 스텝/s입니다(시간당 약 200만 스텝).
  - 같은 컨트롤러의 결과(11/20 골)가 그대로라 물리가 바뀌지 않았음을 확인했습니다.

### 보상 보강 1: 터치·막힘·밀기·시간 초과 (2026-11-24)
처음 버전에 공 터치(+0.1), 막힘(−0.03), 상대 밀기(−0.05), 시간 초과(−1)를 추가하고, 1단계를 처음부터 다시 학습했습니다.

### 보상 보강 2: "공 뒤로 돌아가기" 유도 (2026-11-24, 1단계 v1 → v2)
- **증상:**
  - 1단계 v1은 학습 보상이 −20에서 −3까지 빠르게 올랐습니다.
  - 그런데 35만 스텝부터 −3 근처에서 멈췄고, 골 비율도 5~10%에 머물렀습니다(70만 스텝).
  - 시도 대부분이 30초 시간 초과로 끝났습니다(평균 길이 약 280스텝).
- **분석:**
  - 공을 넣으려면 먼저 **공의 골대 반대편으로 돌아가야** 합니다.
  - v1 보상은 "공에 다가가기"와 "공을 골대 쪽으로"뿐이었습니다. 공 앞쪽에서 다가가면 공을 우리 골대 쪽으로 밀게 되어 오히려 감점입니다.
  - 그래서 돌아가는 요령을 스스로 찾기 어려웠습니다.
- **해결:**
  - 공→골대 선 위, 공 뒤 12 cm 지점에 가까워질수록 보상을 줍니다(+1/m). 잠재 함수 기반 보상이라 최적 플레이는 바뀌지 않고 학습 방향만 잡아 줍니다.
  - 공 운반 보상을 3에서 5로 올렸습니다.
- v1 기록은 `~/pinky_rl/stage1_v1/eval.csv`에 따로 보관합니다(발표 비교용).

### 허점 발견: 공을 밖으로 차서 일찍 끝내기 (2026-11-24, v2 → v2b)
- **증상:** v2를 10만 스텝 학습했더니 시험 20번 중 85%에서 공을 라인 밖으로 보냈습니다.
- **원인:** 공이 나가면 −1을 받고 그 자리에서 끝났습니다. 끝까지 버티면 시간 감점과 시간 초과 −1로 더 많이 깎였습니다. 그래서 정책이 "빨리 밖으로 차 버리는 편이 손해가 적다"는 것을 배웠습니다. 보상 설계의 대표적인 허점(reward hacking)입니다.
- **해결:** 실제 심판처럼 공이 나가면 −2를 주고 **공을 센터로 옮겨 계속 진행**합니다. 일찍 끝낼 길이 없어서, 공을 밖으로 보내면 손해만 봅니다.

### 학습과 실제 경기의 차이: 라인 가드 (2026-11-24, 1단계 → 2단계)
- **증상:** 1단계 정책(골 85%)을 시뮬 경기에 넣고 규칙 기반 파랑과 붙였습니다. 30분 동안 0골이었습니다.
  - 노랑이 파랑 골대 기둥 옆(+0.65, +0.21)에서 27분 동안 멈춰 있었습니다. 공은 기둥 앞(+0.75, +0.19)에 있었습니다.
  - 공격수 로그에는 `boundary line ahead: stop`이 계속 찍혔습니다.
- **원인:** 학습과 실제 경기에서 라인을 다루는 방식이 달랐습니다.
  - **학습 환경**에서는 라인을 넘으면 감점만 받고, 로봇은 실제로 넘어갈 수 있었습니다.
  - **실제 경기**에서는 라인 가드가 그 방향 이동을 아예 막습니다.
  - 정책은 막혀 본 적이 없어서 같은 행동(골대 옆 라인 쪽 전진)을 계속 내고 계속 막혔습니다.
- **해결:**
  1. **학습 환경에도 같은 라인 가드를 넣었습니다**(`_over_line_ahead`). 로봇이 다음에 지나갈 띠가 바깥 라인을 넘으면 전진·후진을 0으로 합니다(골문 앞 제외). 이제 정책이 막히는 상황을 겪으며 배웁니다.
     - 1단계 정책을 가드를 켜고 시험하니 골 85% → 70%였습니다. 2단계에서 적응시킵니다.
  2. **공격수 안전장치:** RL 모드에서 가드에 1.5초 넘게 막히면 1초 동안 경기장 중앙 쪽으로 돌았다가 정책에 다시 맡깁니다(상태 `RL_ESCAPE`).
  3. **심판:** 공이 20초 동안 전혀 안 움직이면(두 로봇이 공 옆에서 막힘) 공만 중앙으로 옮깁니다. 실물에서는 사람에게 안내합니다.

### 2단계 준비 (2026-11-24)
- 1단계 최고 정책(120만 스텝)에서 이어서 학습합니다. 라인 가드는 항상 켭니다.
- 상대는 시도의 60%에서만 뛰고, 나머지 40%는 경기장 밖에 둡니다. 혼자 넣는 실력을 잊지 않게 하기 위해서입니다.
- 1단계에서 상대 위치 입력 2개는 늘 0이었습니다. 그대로 두면 입력 정규화 통계의 분산이 0에 가까워서, 상대가 처음 나타날 때 값이 폭주합니다. 그래서 2단계 시작 때 분산을 0.25로 다시 잡았습니다.

### 2단계 정체 → 상대 속도 커리큘럼 (2026-11-24, 2단계 v1 → v2)
- **증상:**
  - 2단계 v1(120만 → 200만 스텝, 약 1시간)에서 학습 보상이 −1~−3에서 오르내리며 정체했습니다.
  - 시험 결과도 골 35~55%, 자책골 5~40%로 크게 흔들렸습니다.
- **분석:**
  - 상대가 처음부터 정해진 속도(0.2 m/s)로 공을 우리 골대 쪽으로 밉니다. 막 수비를 배우기 시작한 정책에게는 너무 어려운 상대였습니다.
  - 시험 20번 중 상대가 나오는 시도는 일부라서, 수비 실력을 재기에는 표본이 너무 적었습니다.
- **해결:**
  1. **상대 속도 커리큘럼:** 0.12 m/s에서 시작합니다. 학습 중 상대가 나온 시도에서 자책골이 20% 미만이 되면 0.03 m/s씩 올립니다(최대 0.25). 초보에게 약한 상대부터 붙여 주고 단계를 올리는 방식입니다.
  2. **시험 방식:** "혼자 20번 + 상대(정식 속도 0.2 m/s) 20번"으로 나눠서 따로 기록합니다. 시험 속도를 고정해서 회차끼리 비교할 수 있게 했습니다.
- 2단계 v1의 최고 정책(180만 스텝)에서 이어서 학습합니다. v1 기록은 `~/pinky_rl/stage2_v1/`에 보관합니다.

### 3단계 설계: 수비 + 셀프 플레이 (2026-11-24)
2단계는 혼자 골 95%까지 갔지만, 공을 우리 골대 쪽으로 미는 상대에게 자책골이 25~40%였습니다. 원인과 대책은 다음과 같습니다.

1. **공 속도를 모름:** 입력이 공 "위치"뿐이라 공이 어디로 굴러가는지 알 수 없었습니다.
   → 공 속도 입력 2개를 추가했습니다(입력 17 → 19).
   - 실제 경기에서도 카메라 공 위치의 변화로 같은 방식으로 계산합니다(`rl_policy.py`).
   - 학습한 신경망은 버리지 않고 **입력층만 넓혔습니다.** 새 입력의 가중치를 0으로 두면 처음에는 2단계 정책과 똑같이 움직이고, 거기서부터 속도 입력을 쓰는 법을 배웁니다.
2. **수비 위치를 배울 계기가 없음:**
   → 공이 우리 진영에 있고 상대가 공에 더 가까우면, 공과 우리 골대 사이 지점으로 가는 것에 보상을 줍니다.
   - "그 시점의 목표 지점"을 기준으로 이전 위치와 지금 위치를 비교해서, 목표가 바뀌어도 보상이 튀지 않게 했습니다.
3. **상대가 단조로움:** 규칙 상대는 늘 같은 방식으로만 밉니다.
   → **셀프 플레이:** 상대가 나오는 시도의 절반은 학습된 정책의 고정 복사본이 파랑으로 뜁니다.
   - 처음 복사본은 2단계 정책이고, 50만 스텝마다 그 시점의 정책으로 바꿉니다.
   - 파랑 복사본도 노랑과 똑같은 감각(카메라 시야, 공 기억)과 라인 가드를 씁니다. 좌표만 180° 돌려서 봅니다.
4. **시험:** 회마다 세 가지를 20번씩 합니다. 혼자 / 규칙 상대(0.2 m/s) / 2단계 정책(고정). 고정 상대라 회차끼리 비교할 수 있습니다.

학습 환경은 상대를 노랑·파랑 어느 쪽에서든 계산할 수 있게 정리했습니다. 2단계 정책을 새 환경에서 다시 시험해 보니 혼자 골 95%로 같았습니다. 규칙 상대에게 골이 25% → 10%로 바뀐 것은, 이제 그 상대도 라인 가드를 지키기 때문입니다.

### 충돌 금지: 로봇 가드 (2026-11-24, 3단계 v1 → v2)
- **요청:** 로봇끼리 부딪히면 망가지거나 뒤집어질 수 있으니 충돌을 없애야 합니다.
- **확인:** 3단계 v1 정책으로 상대와 16번 시험했습니다(가드 없음).
  - 로봇끼리 닿아 있던 시간이 **전체의 8%**였습니다.
  - **1번은 로봇이 뒤집혔습니다.**
- **해결:** 라인 가드 때 배운 대로 **학습과 경기에 같은 규칙**을 넣었습니다.
  1. **로봇 가드:** 상대 로봇이 진행 방향에 있으면 중심 거리 0.32 m부터 줄이고 0.20 m에서 멈춥니다. 범퍼 사이 약 5 cm입니다.
     - 후진도 같고, 제자리 회전은 허용합니다.
     - 함수 하나(`rl_policy.robot_guard`)를 학습 환경과 공격수가 같이 씁니다.
     - 공격수에서는 규칙 기반이든 RL이든 **모든 속도 명령**에 적용합니다(`striker._robot_guard`, 상대 위치는 라이다 추정).
  2. **보상:** 상대와 닿아 있는 매 스텝 −0.2, 30° 넘게 기울면 −10과 함께 시도를 끝냅니다.
- **결과 (같은 16번):** 가드를 켜니 접촉 **8% → 0%**, 넘어짐 **1 → 0**.
- 3단계 v1의 최고 정책(210만 스텝)에서 이어서 학습합니다. v1 기록은 `~/pinky_rl/stage3_v1/`에 보관합니다.

### 상대 로봇을 장애물로: 큰 충돌 감점 (2026-11-24, 3단계 v2 → v3)
- **배경:**
  - 가드만 있으면 정책은 상대 쪽으로 그냥 달리고, 가드가 대신 세워 줍니다.
  - 그러면 라인 가드 때처럼 막혀서 멈추는 일이 생길 수 있습니다.
  - 그래서 "상대 로봇을 장애물로 보고 스스로 피하기"를 배우게 합니다. 가드는 마지막 안전장치로 남겨 둡니다.
- **감점:**
  - 충돌 순간 **−5**
  - 접촉 중 매 스텝 −0.2
  - 가까움(25 cm 이하) 매 스텝 최대 −0.05
  - 가드에 막힘 −0.05
- **너무 겁먹지 않게:**
  - 처음에는 30 cm부터 감점하려고 했습니다.
  - 그런데 시험해 보니 두 로봇이 공을 두고 30 cm 안에 있는 시간이 59%였습니다. 이 정도면 공 다툼 자체를 피하게 될 수 있습니다.
  - 그래서 25 cm부터 작게 감점하도록 줄였습니다.
- 시험 항목에 충돌 횟수(시도당)와 가까운 시간 비율도 추가했습니다.

### 공 앞에서 둘 다 멈춤 → 공에 가까운 로봇 우선 (2026-11-24, 3단계 v3 → v4)
- **증상:** 공을 가운데 두고 두 로봇이 나란히 공을 보면 둘 다 공으로 가지 않았습니다.
  - 서로가 상대의 진행 통로 안에 있어서, 로봇 가드가 양쪽을 똑같이 세웠습니다.
  - 가까우면 감점도 받으니 둘 다 양보했습니다.
- **해결 (사용자 제안):** 공에 더 가까운 로봇이 먼저 갑니다(`rl_policy.has_priority`).
  - 통신 없이 각 로봇이 혼자 판단합니다. 내 공 거리는 카메라로, 상대의 공 거리는 라이다로 잡은 상대 위치와 공 위치로 계산합니다.
  - 3 cm 이상 더 가까운 쪽이 우선이고, 거의 같으면 실제 경기에서는 노랑이 우선입니다. 학습에서는 시도마다 무작위로 정합니다.
  - **우선권이 있으면** 가드가 중심 거리 17 cm까지 허용합니다(범퍼 사이 약 2 cm). "너무 가까움" 감점은 18 cm부터만 받습니다.
  - **양보하는 쪽은** 24 cm에서 멈춥니다.
  - 멈추는 거리가 서로 달라서 둘이 동시에 서는 일이 없습니다. 학습 환경, 규칙 기반 공격수, RL 공격수에 모두 같은 규칙을 넣었습니다.
- **확인 (나란히 서서 시작하는 12가지 상황, 3단계 v1 정책 그대로):**
  - 5초 안에 공이 움직인 경우: 11/12 → 12/12
  - 접촉: 0
  - 이 규칙으로 다시 학습한 뒤의 결과는 아래 3단계 v4 표에 기록합니다.
- 추가 아이디어: 공이 범퍼 바로 앞(약 10 cm 이내)이면 카메라에 안 보입니다. 이때 초음파 센서 거리로 보완할 수 있습니다(실물 시험 때 적용 예정).

### 회전하며 공 끌기 → "뒤로 넉넉히 돌아가 방향 맞추고 곧게 밀기" (2026-11-24, 3단계 v4 → v5)
- **증상 (사용자 관찰):** 공에 붙은 채 제자리 회전으로 공 방향을 바꾸는 드리블을 했습니다.
  - 시뮬에서는 ㄷ자 범퍼가 공을 감싸서 이게 됩니다.
  - 실물에서는 회전하는 순간 공이 범퍼에서 굴러 나갈 가능성이 큽니다.
  - 측정해 보니 3단계 v1 정책은 **공에 닿아 있는 시간의 32%**를 0.8 rad/s 넘게 회전하고 있었습니다.
- **해결:** 실물에서 되는 드리블, 즉 "공 뒤로 넉넉히 지나간 뒤 → 회전해서 방향을 맞추고 → 곧게 밀기"를 배우게 했습니다.
  1. 공에 닿은 채 0.8 rad/s 넘게 회전하면 매 스텝 최대 −0.1을 줍니다.
  2. 공에 닿아 있고 로봇 방향이 "공 → 골대"와 20° 이내면 매 스텝 +0.02를 줍니다.
  3. "공 뒤 지점" 목표를 12 cm에서 **18 cm**로 늘렸습니다. 공 옆을 스치듯 돌지 않고 충분히 뒤로 가게 유도합니다.
- 시험 항목에 "공에 닿은 시간 중 회전한 비율"(`spin_touch`)을 추가했습니다. 시작 값은 32%입니다.

### 감점이 너무 많아 머뭇거림 → "경기 흐름 우선" (2026-11-24, 3단계 v5 → v6)
- **증상:** v5(250만 스텝, 44분)에서 평균 보상이 −8~−13으로 정체했습니다.
  - 화면으로 본 최근 30번: 골 11, 자책골 4, **30초 동안 골 없음 15**.
  - 흐름을 재 보니 **공을 2초 넘게 못 본 시간이 22~27%**로 가장 큰 문제였습니다(멈춰 서 있음은 0~6%).
  - 감점 피하기를 배우느라 소극적으로 변한 것으로 판단했습니다.
- **목표 (사용자):** 세세한 기술보다, 둘 다 멈추거나 공을 못 찾는 상황 없이 **경기가 잘 굴러가게**.
- **변경 (학습):**
  - 안전과 무관한 감점을 낮췄습니다.
    - 공 닿은 채 회전: 1.2 rad/s부터, 최대 −0.05
    - 너무 가까움: 양보하는 로봇만 24 cm 안에서 최대 −0.03
    - 가드에 막힘: −0.02
  - 흐름 감점을 추가했습니다.
    - 1초 넘게 거의 안 움직임: 매 스텝 −0.02
    - 공을 2초 넘게 못 봄: 매 스텝 −0.01
  - 충돌 −5와 로봇 가드는 그대로 둡니다(파손 방지).
- **변경 (경기 코드, 안전장치):** RL 모드에서 공을 **3초 넘게 못 보면 기존 규칙 기반 공 찾기**(뒤로 → 제자리 회전 → 경기장 돌아다니기)로 바꿉니다. 공을 찾으면 다시 정책이 맡습니다(`rl_search_after`).
- 시험 항목에 시간 초과 비율, 멈춤 비율, 공 못 본 비율을 추가했습니다.
  - v5 정책 기준 (혼자 / 2단계 정책 상대):
    - 시간 초과 20% / 60%
    - 멈춤 0% / 6%
    - 공 못 봄 22% / 27%
- v5의 최신 정책(250만 스텝)에서 이어서 학습합니다. v5 기록은 `~/pinky_rl/stage3_v5/`에 보관합니다.

### 경기 A / B: 학습 정책 비교, 회전 지연 보정, 우선권 깜빡임 (2026-11-24 밤)
학습 수치가 정체해서, "경기가 잘 굴러가는지"를 실제 경기 시뮬로 직접 확인했습니다. 상대는 모두 규칙 기반 파랑입니다.

| 경기 | 노랑 정책 | 설정 | 결과 | 흐름 문제 |
|---|---|---|---|---|
| A | 2단계 정책 | 이전 설정 | 1 : 2 (약 8분에서 중단) | 공 20초 정지 2회, 라인 붙은 공 2회, 골대 옆 아웃 3회 |
| B | 3단계 v6 정책 (290만 스텝) | **새 설정** | **2 : 0** (약 4분에서 중단) | 라인 붙은 공 1회, 골 뒤 골대 끼임 1회 |

경기 중 관찰과 사용자 의견으로 고친 것:
1. **회전하면 공 위치가 틀어짐:**
   - 공 위치를 계산할 때 "지금" 로봇 방향을 쓰고 있었습니다. 사진을 찍고 처리하는 데 약 0.1초가 걸리는데, 그 사이 3 rad/s로 돌면 1 m 앞 공이 옆으로 약 30 cm 틀린 곳에 찍힙니다.
   - **사진을 찍은 시각의 로봇 방향**으로 계산하도록 바꿨습니다(`ball_detector._tf_at`, 흰 라인 기억도 같음).
   - 로봇과 PC의 시계가 안 맞아 그 시각의 위치를 찾을 수 없으면, 이전 방식(지금 방향)으로 계산합니다.
2. **우선권이 1초에 여러 번 바뀜:**
   - 두 로봇의 공 거리가 비슷하면 "내 차례/양보"가 계속 뒤집혀서 둘 다 머뭇거렸습니다.
   - 한 번 우선권을 가지면 상대가 **6 cm 이상 더 가까워질 때까지** 유지하도록 바꿨습니다(히스테리시스, 학습 환경도 같음).
3. **파랑이 둔함 (사용자):** 규칙 기반 공격수의 속도를 올렸습니다.
   - 최대 회전 1.2 → 2.0 rad/s
   - 공 찾기 회전: 실물 0.6 → 0.9 rad/s, 시뮬 1.2 → 1.5 rad/s
   - 다가가기·드리블: **최고 속도 0.28 m/s** (이전 0.22 / 0.15)
4. **공을 못 찾는 상황 (흐름):** RL 모드에서 공을 3초 넘게 못 보면 규칙 기반 공 찾기로 바꿨다가, 공을 찾으면 다시 정책이 맡습니다.
5. **선공 (사용자):** 경기 첫 출발은 노랑이 먼저 하고, 파랑은 3초 뒤 출발합니다(`first_kick`). 골 뒤 재시작은 이전처럼 직전 득점 팀이 3초 뒤 출발합니다.

## 7. 실제 경기에 연결하기 (rl_striker)

1. **내보내기:** `pinky_soccer_rl/export.py`가 PPO 정책(PyTorch)을 numpy 파일(`.npz`)로 바꿉니다. ROS 쪽 파이썬에는 PyTorch가 없기 때문입니다.
   - 신경망: 256-256 Tanh, 행동은 평균값
   - 입력 정규화 통계(VecNormalize)도 같이 저장합니다.
   - 내보낼 때 stable-baselines3 결과와 비교해서 차이가 1e-4를 넘으면 실패 처리합니다. 실제 차이는 2.8e-7이었습니다.
2. **실행:** `pinky_soccer_game/rl_policy.py`
   - `MLPPolicy`: numpy로 신경망을 계산합니다.
   - `RLPlayer`: 공격수가 가진 정보(AMCL 위치, 카메라 공 위치와 기억, 라이다 상대 위치)로 **학습 환경과 똑같은 17개 입력**을 만듭니다.
3. **공격수에 연결:** `striker.py`에 `policy_path`를 주면, 경기 중(PLAY) 판단만 정책이 맡습니다(상태 `RL_PLAY`).
   - 그대로 유지: 준비·READY·세레모니·실점 후 비키기·득점 후 3초 대기, 흰 라인 가드
   - 정책은 학습과 같은 0.1초마다 새 행동을 내고, 그 사이에는 같은 명령을 반복합니다.
4. **파랑:** 정책은 노랑(+X 공격)으로 학습했습니다. 모든 좌표를 "공격 방향 기준"으로 돌려서 같은 정책을 파랑(−X 공격)에도 씁니다.
5. **검증 (학습 환경에서 오프라인으로):**
   - RLPlayer가 만든 입력과 학습 환경 입력의 차이는 6e-8입니다.
     처음에는 "공을 아직 못 봤을 때" 값이 달랐습니다. 학습 환경은 경기장 중앙을 넣는데 RLPlayer는 0을 넣었고, 학습 환경에 맞게 고쳤습니다.
   - 좌우·앞뒤를 뒤집은 파랑 상황에서 같은 행동이 나옵니다(차이 1e-10).
   - numpy 정책만으로 돌렸을 때 20번 중 14골(70%)이었습니다.
6. **시뮬 경기 연결 시험 (2026-11-24):**
   - 노랑 = RL 정책, 파랑 = 규칙 기반으로 붙였습니다.
   - 경기 진행 → READY → `RL_PLAY` 전환, 위치 추정(오차 6 cm 이하), 공 몰고 가기까지 정상 동작했습니다.
   - 학습과 동시에 돌려서 CPU가 포화(부하 35)되는 바람에 실력 비교는 하지 못했습니다. 학습을 마친 뒤 따로 다시 시험할 예정입니다.
